# mock_CPU

用软件自底向上模拟 8 位 CPU：感知机逻辑门 → 加法器 → ALU → 时序部件 → 存储部件 → 指令集与整机（已跑通），附迷你汇编器。

## 结构

- `ALU/` — 组合算术部件
  - `gate.py` 基本逻辑门（纯 Python 算术，~0.2µs/门；原 numpy 感知机版见 git 历史，26× 提速，197 万项穷举验证数学等价）
  - `full_adder.py` 半加器 → 全加器 → 8 位行波进位加减法器（补码减法）
  - `alu.py` 11 种运算 + Z/N/C/V 标志位
  - `test_alu.py` 穷举测试（197 万项断言）
- `COMB/` — 通用组合部件
  - `mux.py` 门级 2 选 1 / one-hot AND-OR 阵列 / 字级多路选择器
  - `decoder.py` n → 2^n one-hot 译码器（带使能端）
  - `test_comb.py`
- `SEQ/` — 时序部件
  - `dff.py` D 触发器 + 时钟（行为级：显式状态 + 边沿统一提交）

## 架构与数据通路

分层依赖（自底向上搭建，箭头方向即 import 方向，永不反向）：

```
第 5 层 集成        CPU/cpu.py                          ← 唯一 import 四个部件包的文件（塔尖）
第 4 层 规格与语义   CPU/isa.py · CPU/control.py          ← 零依赖的纯定义（指令编码 / 微程序表）
第 3 层 系统部件     SEQ/register_file.py · SEQ/pc.py · MEM/ram.py
第 2 层 功能部件     SEQ/register.py · COMB/mux.py+decoder.py · ALU/full_adder.py · ALU/alu.py
第 1 层 原语        SEQ/dff.py（记忆之根）· ALU/gate.py（组合之根）
```

三条架构铁律：依赖严格单向（部件包不知道 CPU 的存在）；isa/control
不依赖任何部件（纯规格，换实现不动规格）；跨包 import 仅 6 条（耦合面刻意收窄）。

一条指令的旅程（`CPU.step()` 五步，声明与提交分离）：

```
PC ─地址→ RAM.read×2 ─op,arg→ isa.decode → control.signals（微码六信号）
                                             │
RF.read（门级 MUX 译码选择）─A,B→ ALU ─结果+标志┤
      │                             ├→ RF.write / RAM.write（声明）
      │                             └→ 4×DFF 标志位（声明）
      └→ PC 下一拍：add8(pc,2) 顺序 / load(目标) 跳转（声明）
                              ↓
                   clk.tick() ← 全机唯一提交点：PC、寄存器、RAM、标志同时翻转
```

测试金字塔：ALU 197 万项穷举打底，向上 COMB 109、SEQ 18+23+9、MEM 11、
CPU 222——底层全绿，上层失败只需查上层。

## 第一个程序

`first_program.py` 是上手示例：用助记符辅助函数拼出"5! = 120"的阶乘循环，
带指令跟踪运行，结果写入内存 0x80。在项目根目录执行 `python first_program.py` 即可。
核心骨架（每条指令恰好 2 字节，第 k 条位于地址 2k——**注释标地址、跳转目标按此手算**，
这是手工汇编的基本功）：

```python
from CPU import isa
from CPU.cpu import CPU

prog = (isa.I_LDI(0, 5) +          # 0x00: R0 = n = 5
        isa.I_LDI(1, 1) +          # 0x02: R1 = acc = 1
        isa.I_ALU("MUL", 1, 0) +   # 0x04: acc *= n
        isa.I_UN("DEC", 0) +       # 0x06: n -= 1（更新标志）
        isa.I_JMP("JNZ", 0x04) +   # 0x08: n≠0 则回 0x04
        isa.I_ST(1, 0x80) +        # 0x0A: 结果写入内存 0x80
        isa.I_HALT())              # 0x0C

cpu = CPU(prog)
n, halted = cpu.run(trace=True)    # 逐条打印指令、寄存器与标志
print(cpu.rf.read(1), cpu.ram.read(0x80), cpu.flags())
```

写自己的程序就是这三步：**`isa.I_*` 拼字节 → `CPU(prog)` 装载 → `run(trace=True)` 执行**。
随时用 `cpu.rf.read(i)` / `cpu.ram.read(addr)` / `cpu.flags()` 观察状态；
单步调试可循环调用 `cpu.step()`。约定：程序放低地址、数据从 0x80 起，
256 字节共用一块内存。

## 第二个程序：让机器打印字符

`second_hello.py`（`python second_hello.py`，输出 `HELLO, MOCK_CPU!`，98 条指令）
**不给 CPU 增加任何东西**就实现了输出，靠两个经典概念：

- **内存映射 I/O**：约定地址 0xFE 是"控制台端口"，往它写字节就显示一个字符。
  程序继承 RAM 造了一颗带屏幕的内存（`ConsoleRAM`），CPU 以为自己只是在
  做普通的 ST——设备挂在总线上"冒充"内存，这正是真实计算机的 I/O 方式
  （C64 的屏幕、串口芯片的寄存器都是这么接的）
- **自修改代码**：本机 LD/ST 只有直接地址、没有指针寻址，无法遍历字符串。
  解法是循环里把新地址写回那条 LD 指令的地址字节（指令与数据同片内存，
  冯·诺依曼结构的本义）——程序运行中改写自己。这是早期程序员的日常，
  也是现代 CPU 的禁忌（指令缓存与流水线不一致，x86 遇到必须冲刷流水线）

## 第三个程序：帧缓冲"屏幕"

`third_screen.py`（`python third_screen.py`）造出了一块"真·屏幕"——同一个
程序里对照演示两种输出模型。设备约定（CPU 依然不知情）：`0x90~0x9F` 共
16 字节是**帧缓冲**（这片内存"就是"屏幕），`0xFE` 字符流端口打一个字符，
`0xFD` 回车端口换行。

- **teletype vs framebuffer**：标题 `DEMO:` 走流式端口——"写一个打一个"，
  输出是流水；进度条走帧缓冲——渲染器读内存的**当前状态**作画，屏幕显示
  "存着什么"而非"来过什么"，所以格子可以被反复改写、就地更新。这是显存
  相对打印机的本质能力（C64 屏幕内存、显卡显存同理）
- **刷新与写入异步解耦**：渲染不在写钩子里，而由驱动端的刷新循环按圈触发
  ——对应真实显卡"CPU 随便写、显示器按场频自己扫"的工作方式
- 填格子复用自修改代码技巧（指针写回 ST 指令的地址字节）

## 第四个程序：多字节加减法

`fourth_multibyte.py`（`python fourth_multibyte.py`）在没有 ADC/SBB 指令的机器上
做 16 位加减法，6 组差分用例全过（含进位链、16 位溢出、借位链）。核心问题：
**进位必须跨字节传递，但每条 ADD 都会覆盖 C 标志**。解法：

- **进位不放标志里，放寄存器里**（R2 传递）：每字节"带进位加"分两步——
  先 `ADD` 并趁 C 还在立即分支落进 R2；再补 cin：`R0==255` 时回绕并再置进位，
  否则安全 +1。进位输出 = 两股进位在寄存器里汇合
- 减法对偶：借位判定用 `JNC`（SUB 的 C 是借位取反），回绕检测 `R0==0` 再减
- 每字节 ~14 条指令——写完就懂了真实 CPU 为什么都有 `ADC`/`SBB`（1 条顶 14 条），
  这是本机 ISA 最有资格的扩展候选

## 第五个程序：软件除法

`fifth_division.py`（`python fifth_division.py`）用**移位相减（恢复余数法）**实现
8 位 ÷ 8 位 = 商 + 余数，8 组精选 + 11×11 全矩阵共 121 组差分全过。算法与
8086 `DIV` 指令的微码同构，21 条指令：

- 每轮处理被除数一位：`SHL R0` 把被除数最高位顶进 **C 标志（移位窗口）**，
  `SHL R1` 再把它从 bit0 注入余数（两次移位间 C 会被覆盖，需分支先落地）；
  然后 CMP 试减——够减则 SUB、商本位置 1，不够则跳过（"恢复"）
- **为什么 8 位机除法靠软件**：加减是并行链、乘法是单向阵列（部分积可一次
  展开，一拍完成），而除法每一位依赖上一位试减的结果——带反馈的迭代，
  硬件要么做多拍状态机、要么单拍级联 8 级比较减法拖慢全机时钟；加上晶体管
  预算紧（6502 约 3500 管）和除法需求稀少，历史选择就是软件子程序。
  6502/Z80/8051 均无 DIV，ARM 与 RISC-V 基础指令集也长期不含除法
- 开发花絮：手算跳转地址偏了 2 导致死循环——"该做汇编器"的活案例

## 第六个程序：XOR 花纹（Munching Squares）

`sixth_munch.py`（`python sixth_munch.py`，全程约 5 秒）复刻 1962 年 PDP-1 上的
祖师爷级 demo：把 `x XOR y` 铺满屏幕，阈值流动时花纹层层生长又坍缩——"啃食"
由此得名，后收录于 MIT 的 HAKMEM 备忘录，是 demoscene 的起点。8 位机的 3 位
XOR 恰好铺满 8×8 网格——这台机器和这个图案天生一对。

- **机器侧**（547 条指令）：双重循环算 64 格的 x^y 值进帧缓冲 0xC0~0xFF；
  遍历用自修改指针——`ST R6,[0x0D]` 每格改写 ST 指令自己的地址字节，
  **这就是指针的本相**：地址存在寄存器里、每步 +1、间接决定落点
  （无间接寻址指令的机器用自修改模拟它）
- **显示侧**（Python 驱动）：帧缓冲存的不是 0/1 而是"本格的 XOR 值"，
  渲染以阈值 t 扫描——值 < t 点亮；t 逐帧上升，对角线 → 方阵 → 四象限 →
  全亮 → 坍缩。程序与显示异步解耦 = PDP-1 的 CRT 持续刷新、程序只写内存

## 输出三部曲的共性（②③⑥）

`second_hello` / `third_screen` / `sixth_munch` 是同一主题的三次变奏，共享三件套：

- **设备冒充内存**：屏幕/控制台不是机器的一部分，是 Python 侧的地址约定——
  ② write 钩子（端口 0xFE）→ ③ 读写混合（端口 + 帧缓冲）→ ⑥ 纯读侧观察
  （零钩子），设备越来越被动，CPU 与 ISA 全程零知情
- **自修改代码当指针**：三者都在遍历内存（字符串/格子/表格），无间接寻址的
  机器把指针刻进指令的操作数字节、每步改写（②改 LD，③⑥改 ST）
- **写入与显示异步解耦**：程序只管把数据摆进内存，显示按自己的节奏扫描
  ——PDP-1 的 CRT 模型，⑥ 推到极致（机器算完即 HALT，动画全在显示侧）

谱系即历史：② teletype 流式（写一个打一个）→ ③ 帧缓冲（显示"存着什么"）
→ ⑥ 纯数据 + 显示端动画——从打字机到显卡的输出进化路线，1962 年至今。

## 第七个程序：Core War 核心大战

`seventh_corewar.py`（`python seventh_corewar.py`，约 10 秒）复刻 1984 年的
程序角斗：**蠕虫 vs 轰炸机**，两颗 CPU 共享同一片 RAM 轮流各走一步（MARS
进程模型），轰炸机向中场投非法操作码炸弹，谁先让对方执行到非法指令谁胜。

- **蠕虫 = "常驻引擎 + 蛙跳入口"**（自复制程序的落地形态）：引擎 18 字节
  永不搬家（绝对地址永远有效——这正是绝对跳转 ISA 上纯 imp 不可能、而
  此变体可行的原因），每代 LDX/STX 把身体拷到前方，再用一条 STX **把自己
  JMP 的地址字节改成新副本首址**（间接寻址与自修改联手），跳进去再蛙跳
- **纯 imp 为何不可能**：Redcode 的 `MOV 0,1` 一条指令爬行靠的是"PC 随
  复制前进"的游戏专属设计；我们的绝对跳转 ISA 里副本的跳转目标全失效——
  这也是真实病毒需要相对跳转/重定位的原因
- 确定性对战：固定布局下结果可复现（本局第 1239 拍蠕虫铺到轰炸机获胜）
- 花絮：首跑"裁判误判"——蠕虫每代合法自改 JMP 字节，被朴素逐字节完整性
  检查当成"被炸"；修复 = 完整性比对豁免自改字节

## 第八个程序：输入端口与回声机

`eighth_echo.py`（`python eighth_echo.py`）开通 **0xFC 输入端口**——第一块
"全双工"外设 `ConsoleKeyboardRAM` 同时钩住 `read()`（读 0xFC = 取键）与
`write()`（写 0xFE = 打字符），与输出三件套的 write 钩子互为镜像，
I/O 全家福凑齐。

- **约定**：读 0xFC 为破坏性读取（如真实键盘数据寄存器），队列空返回
  0 = "无键"哨兵；键码存 ASCII——字符 '0' 是 48，与哨兵 0 互不相扰
  （若需输入 NUL 字节，升级方案是 0xFB 状态端口，信令移到带外）
- **轮询**：机器无中断，等键靠 `CMP/JZ` 忙等——1970-80 年代键盘的真实
  工作方式；驱动端预投喂按键（剧本式输入），确定性保留
- 两幕自校验通过：回声机（投喂 HELLO → 回声 HELLO → 停机）、按键分支
  （'1'→A / '2'→B / 'Q'→退出，输入驱动控制流）——解锁贪吃蛇、
  Breakout、猜数字、迷你 Eliza 等交互程序

## 第九个程序：贪吃蛇

`ninth_snake.py`（`python ninth_snake.py` 剧本回放 + 差分自校验；
`python ninth_snake.py --play` 真人 WASD/方向键操控）。机器侧 92 条指令
（184 字节）+ 驱动端渲染/时钟，复古节奏约 1 FPS（未做 gate.py 提速的
方案 B）。

- **键盘即时钟**：机器阻塞等键，驱动端每拍投喂两个"增量键码"
  （dx+2、dy+2 ∈ {1,2,3}，避开 0=无键哨兵）——机器侧省掉整个方向分派
- **帧缓冲即蛇身**：8×8 场地 0xC0~0xFF，蛇身格存"年龄"（头=1，每拍 +1，
  超过蛇长即清零=尾巴缩回），食物=255；单一数据结构零重复记账
- **食物**：机内 Galois LFSR（种子 1，抽头 0xB8），落在非空格则重抽
- **开局烧写**：初始局面全部由 `.db` 摆好，机器只初始化 3 个寄存器
- **验收**：剧本回放与 Python 参考实现逐格差分（两套独立实现，最终
  棋盘/分数/结局必须一致）——分数 2:2、64 格一致、第 25 拍撞墙
- 花絮：食物标记初版设 250，被 `INC` 检测法当场戳穿——250+1=251 不回绕，
  255+1 才归零（哨兵值与检测算法必须配套）

### v1.1（`ninth_snake_v1_1.py`）——修复防掉头双连转漏洞

两个版本的默认模式不同（v1.1 的身份是"修复验证文件"）：

| 命令 | v1（ninth_snake.py） | v1.1（ninth_snake_v1_1.py） |
|------|---------------------|---------------------------|
| `python xxx.py` | 剧本回放 + 差分自校验（棋盘动画） | **三幕验收**（回归/立此存照/修复证明） |
| `python xxx.py --play` | 真人操控 | 真人操控 + 方向仪表盘 |

v1 的防掉头参照物是"最新意向 cur"而非"实际投喂方向"——同一采样窗口内
快速按两个键（如上行时 A+S）可让第二个键对照第一个"幽灵转向"通过检查，
机器实际收到 180° 反向 → 一拍撞死自己（用户实测发现）。

- **修复**：拆 cur 为 `last_fed`（上一拍实际投喂——防掉头的唯一参照，
  仅在投喂后更新）+ `pending`（下一拍意向）；防线只认"已执行"——
  意向转两次骗不过执行才走一步。附带修复死亡拍双重渲染
- **方向仪表盘**：每帧显示 `当前:↑ 下一:← ★`——当前=last_fed（实际
  走的方向）、下一=pending（便签上的意向）、★=两者不同（转向待执行）。
  按键后"下一"立即变、"当前"下一拍才跟上——"慢一拍"的因果链可视化
- **三幕验收**：① 回归——v1.1 跑 v1 同一剧本的差分依旧逐格一致（机器侧
  零改动）；② 立此存照——内联复刻 v1 旧防线喂 A+S，bug 必然发生
  （文档化）；③ 修复证明——新防线拦截 's'，游戏级注入 A+S 蛇存活

### v1.2（`ninth_snake_v1_2.py`）——★ 仪表盘修复

v1.1 的 ★ 永远不亮：循环里 `last_fed = pending` 在 render 之前执行，
渲染时两者恒等。v1.2 把循环重排为 **tick → sample → render**——先执行
这一拍、再采样下一拍按键、最后渲染；渲染时 last_fed（刚走完）和
pending（刚采样的下一拍意向）自然可能不同，★ 在"转向已排队但尚未
执行"的窗口里亮起。机器侧零改动，三幕验收依旧全过。

### v1.3（`ninth_snake_v1_3.py`）——固定步长累加器

gate.py 提速后机器每拍仅 ~14ms，v1.2 的 sleep(0.12) 节奏过快（~7 FPS），
玩家反应不过来——与红警等老游戏在高速 CPU 上"AI 太快"同病根：
帧率绑定了游戏逻辑。

- **修法**：**固定步长 + 累加器**——逻辑更新频率恒定（`TICK_RATE = 4`
  拍/秒），机器全速干完一拍后休眠等待。累加器本质是"时间银行"：
  真实时间存进去，攒够一步的份额就取出来执行一步
- **游戏速度与机器速度完全解耦**（改 `TICK_RATE` 一个常量调速度，
  换机器零调参）；确定性保留（每秒恰好 TICK_RATE 步，差分测试可靠）
- 实测：累加器精确维持恒定节拍（误差 <1ms）
- 真玩模式：`python ninth_snake_v1_3.py --play`（默认 3 拍/秒，改 `TICK_RATE` 调速）

## 指令集（统一双字节：操作码 + 操作数字节）

```
LDI/MOV/LD/ST   数据传送（立即数/寄存器/内存）
LDX/STX         寄存器间接读写（地址 = 指针寄存器内容，Rd←mem[Rn] / mem[Rn]←Rs）
ADD SUB AND OR XOR MUL CMP   R0~R7 寄存器运算，CMP 只更新标志不写回
INC DEC SHL SHR 单目运算（INC/DEC 即 B=1 的 ADD/SUB）
JMP JZ JNZ JC JNC JN JNN JV 条件跳转（消费 Z/N/C/V）
CALL/RET 子程序调用与返回（硬件栈：SP 空栈=0，返回地址压栈，栈从 0xFF 向下生长）
PUSH/POP 压栈/弹栈（保存与恢复现场——递归中"活过下一次调用"的保障，序言/尾声雏形）
HALT 停机；0xF8 预留 DIV
```

## 迷你汇编器（ASM/）

`ASM/asm.py` 用**两遍扫描**把汇编文本翻译成机器码：第一遍用位置计数器（LC）
建符号表（标号 → 地址，标号本身占 0 字节）；第二遍查表生成字节，前向/后向
引用统一解决。编码的单一事实源在 `CPU/isa.py`——全部经 `isa.I_*` 编码，
汇编器零重复实现；九类错误（未定义/重复标号、非法寄存器、缺 `#`/`[]` 等）
**带行号**在翻译期拦截。

语法刻意最小化：标号 `name:`（可与指令同行）、注释 `;`、立即数 `#5`/`#0x1F`、
地址 `[0x80]`（也接受 `[标号]`）、跳转目标直接写标号名；伪指令 `.org`（定位，
只许前进、中间补零）与 `.db`（数据/ASCII 字符串）。指令与 isa 的 24 条一致，
**助记符大小写不敏感**（`ldi` = `LDI`，解析时统一转大写）；**标号名则大小写敏感**
（`loop` ≠ `Loop`，符号表按原样存取）。标号名只需是合法标识符（字母/下划线开头）——名字是翻译期的
脚手架，查表换成地址后即抹除，机器码里只有数字（有蜕变测试守护此性质）。

从此告别手算跳转地址——三个示例程序曾栽过的坑（地址 +2 事故）由机器数数
根除。

```bash
python -m ASM.test_asm                     # 152 项断言（瞬时）
python -m ASM.asm ASM/example.asm          # 翻译：机器码 + 反汇编对照
python -m ASM.asm ASM/example.asm --run    # 翻译 + 上机执行（带跟踪）
```

测试四层：与 `isa.I_*` 的**编码差分**（24 助记符 × 8 寄存器）、标号与伪指令、
错误用例（含行号专项）、**端到端**（汇编 → 上机 → 与 Python 对账：阶乘 120、
累加 15）。示例源码见 `ASM/example.asm`。

## 关键约定

- 8 位字宽、LSB-first 位列表、超出位宽自动截断
- 新机状态确定性全零（8 寄存器/内存/标志/SP 从 0 出发）——测试中寄存器作
  **计数器**用（断言读增量）可依赖零起点免初始化；作**数据载体**用
  （值本身是断言内容）则必须显式 `LDI` 装值
- 时序纪律：组合阶段"读旧值 + d()/write() 声明"，时钟沿 tick() 统一提交；
  同拍读到的永远是旧值
- 标志位 Z/N/C/V（减法 C 为借位取反）；乘法 8x8 → 16 位（存低字节，C=高字节非 0）
- 硬件栈：SP 空栈 = 0，PUSH 即 SP−1 再写（回绕生长到 0xFF），无溢出保护
- I/O 端口约定（设备冒充内存，CPU 零知情，示例脚本内定义）：读 0xFC 取键
  （空 = 0 哨兵）；写 0xFE 打字符 / 0xFD 回车；帧缓冲区按程序各自约定
- 依赖方向自底向上：gate → full_adder → alu；dff → register → register_file/pc；
  部件包不知道 CPU 的存在
